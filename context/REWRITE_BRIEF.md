# Rewrite brief: Room-backed OOP library

## Objective

Replace the old algorithms-course implementation with a production-like Kotlin/JVM + Compose Desktop course project that satisfies the 2026 OOP methodology and persists data with Room 3.

## Non-negotiable acceptance criteria

1. Desktop JVM only. No JS, WASM, browser entry point or Pages deployment.
2. No `BookCipher`, `ReaderTicket`, variant `624`, custom AVL tree, custom hash table, skip list, Boyer–Moore or insertion sort in active source, tests, README, report, slides, diagrams or UI.
3. Forms never ask the user for technical IDs. IDs are opaque UUID strings generated by an injected `IdGenerator`.
4. Clean domain hierarchy with at least six concrete entities: `Reader`, `Librarian`, `Book`, `Periodical`, `LibraryBranch`, `Loan`; abstract/interface roots `LibraryEntity`, `Person`, `Publication`.
5. M:N `Reader ↔ Publication` is implemented through `Loan` and real foreign keys.
6. Room 3 + KSP + bundled SQLite; schema exported. Database file uses an application-data location, not a temporary directory.
7. DAO APIs are `suspend`/`Flow`. Repository interfaces do not expose Room types. Room repositories map persistence records to domain objects.
8. `LibraryService` provides atomic issue/return operations and keeps `availableCopies` consistent.
9. Real patterns, each with test/evidence: Repository, MVVM, Strategy (`LoanPolicy`), Factory, Observer (`Flow`/`StateFlow`), State (`LoanState`), Facade/Application Service.
10. UI manages readers, books/periodicals and loans; it shows human-readable titles/names, loading/error/empty states, validation messages and persistence status.
11. Demonstration data is inserted transactionally and does not duplicate on repeated insertion.
12. Persistence integration test proves write → close → reopen → read, plus update/return behavior.
13. `./gradlew clean test build` succeeds on JDK 17-compatible CI and locally.
14. README contains setup, architecture, patterns, database location, test commands and course-methodology mapping.
15. Typst report and 10–15 slide presentation describe the final Room architecture only and build successfully.

## TDD order

Implement vertical slices and observe each new test fail before production code:

1. domain ID generation, entity validation and hierarchy;
2. `LoanPolicy` Strategy and `LoanState` transitions;
3. Room database smoke/persistence with one entity;
4. complete schema, mappers and repositories;
5. transactional issue and return through `LibraryService`;
6. ViewModels observing repository flows;
7. Compose forms and screens;
8. demo factory/seed operation.
